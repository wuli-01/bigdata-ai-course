🔗 Agent · 上下文 · Skill：三者如何协作

生成日期 2026-09-10 · 按 Skill「concept-crash-course」流程生成并经人工核查

1一句话概括

Agent 是执行者，上下文是它的"工作台"，Skill 是预先放好的"专业剧本"——任务命中剧本时，剧本被摊开到工作台上，Agent 照着高质量的方法把活干完。

🤖 Agent = 厨师自主决定做什么菜、按什么顺序做，遇到问题换方案
🧠 上下文 = 厨师眼前的操作台台面上看得见的食材和订单决定他每一步判断；台面窄、堆太满都会出错
🧩 Skill = 整理好的菜谱卡平时收在抽屉里（不占台面），接到对应菜的单子才抽出来铺在台面上

2对比表：三者各自的角色

维度Agent（智能体）上下文（Context）Skill（技能）
是什么能自主规划、调用工具、多步执行任务的 AI 系统单次推理时模型能"看见"的全部信息，按 token 计量、容量有限以 SKILL.md 为核心的可复用能力包：说明书 + 可选脚本/资料
生命周期长期运行，跨多任务单次请求内有效，会话结束即消失持久保存在仓库/系统中，可版本管理
怎么"进入"上下文—（它是消费者）—（它是容器）平时只常驻一行 description；任务语义命中后按渐进式披露逐层注入
类比厨师操作台菜谱卡

3协作流程图

👤 用户提出任务（如"我想学习 Hadoop 这个概念"）
↓
🤖 Agent 接收目标，开始规划
↓
🧠 组装上下文：系统提示 + 对话历史 + 工具结果
↓
🧩 匹配到 Skill 的 description？命中则渐进式加载 SKILL.md
（平时只占一行字，命中后正文与附属文件才进入上下文）
↓
⚙️ Agent 循环：规划 → 调用工具 → 观察结果
↓
✅ 产出结果（本例中为 learning-materials/hadoop.html）
↺
📝 新经验可固化成新的 Skill（知识资产化，供未来任务命中）

图中"↺"表示飞轮：使用 → 沉淀 → 复用。上下文贯穿 Agent 的每个决策循环。

使用——Agent 按现成 Skill 完成任务
沉淀——把新经验写成新的 SKILL.md
命中——下次同类任务自动匹配到
复用——产出质量一致，成本趋近于零
Skill 沉淀知识的方式：从"每次口述方法"变成"一次编写、永远在线"

4两个重点关系

  1. 上下文如何影响 Agent 的工作？
    Agent 每一步"决定下一步做什么"完全基于当前上下文：报错信息在上下文里，它才知道要修复；历史尝试在上下文里，它才不会重复犯错。因此上下文的质量 = Agent 的智力上限：
    • 缺失关键信息 → 决策错误（桌上没有的它不知道）
    • 塞入无关信息 → 稀释注意力（中间位置的信息最易被忽略，即 Lost in the Middle）
    • 超出窗口容量 → 被截断，早期经历"失忆"
    所以好的 Agent 系统都在做"上下文工程"——像整理操作台一样，把最相关的放开头/结尾，及时压缩清理。
  2. Skill 如何沉淀可复用的任务知识？
    把"某类任务怎么做才专业"从对话流里固化成文件：适用场景写成 description（可被语义匹配）、操作步骤写成 SKILL.md 正文、工具性代码放进 scripts/。
    • 一次编写 → 每次任务命中自动加载 → 输出风格与质量一致
    • 可版本管理、可分享给他人、可跨工具（Agent Skills 已是开放标准）
    本仓库即实例：concept-crash-course 定义了"概念学习资料"的生成流水线，三份资料都是它的产物；下次学习新概念时同一 Skill 直接复用。

5以本仓库学习流程串一遍

  • 我（用户）说："我想学习 Agent 这个概念" —— 任务进入 Agent
  • Agent 在上下文中看到本仓库的 Skill 列表，concept-crash-course 的 description 匹配成功
  • 按Skill 的指导：先上网核实定义（来源进入上下文）→ 按五板块生成 learning-materials/agent.html → 自检 → 提交 git
  • 产出保持统一结构，全过程我只需一句话——这就是三者协作的价值：Agent 负责干，上下文负责记，Skill 负责对
