一句话概括三者关系

Agent 是执行者，上下文是它的"工作台"，Skill 是预先放好的"专业剧本"——任务命中剧本时，剧本被摊开到工作台上，Agent 照着高质量的方法把活干完。

🤖 Agent = 厨师自主决定做什么菜、按什么顺序做，遇问题换方案
🧠 上下文 = 厨师眼前的操作台台面上看得见的食材和订单决定他每一步判断；台面窄、堆太满都会出错
🧩 Skill = 整理好的菜谱卡平时收在抽屉里（不占台面），接到对应菜的单子才抽出来铺在台面上

两个重点关系（作业核心问题）

  1. 上下文如何影响 Agent 的工作？
    Agent 每一步"决定下一步做什么"完全基于当前上下文：报错信息在上下文里，它才知道要修复；历史尝试在上下文里，它才不会重复犯错。因此上下文的质量 = Agent 的智力上限：缺失关键信息会决策错误（桌上没有的它不知道）；塞入无关信息会稀释注意力（Lost in the Middle：中间位置的信息最易被忽略）；超出窗口容量会被截断，早期经历可能"失忆"。所以好的 Agent 系统都在做"上下文工程"——像整理操作台一样，把最相关的内容放在开头/结尾，及时压缩清理。
  2. Skill 如何沉淀可复用的任务知识？
    把"某类任务怎么做才专业"从对话流里固化成文件：适用场景写成 description（可被语义匹配）、操作步骤写成 SKILL.md 正文、工具性代码放进 scripts/。它的复用机制是：一次编写 → 每次任务命中自动加载 → 输出风格与质量保持一致 → 可以版本管理与分享。本仓库就是实例：concept-explainer Skill 定义了"概念学习资料"的生成流水线，本次三份资料 + 这份关系说明都是它的产出；下次学习"Hadoop"时同一 Skill 直接复用。

以本仓库学习流程为例串一遍

  • 我（用户）说："我想学习 Agent 这个概念" —— 任务进入 Agent
  • Agent 在上下文中看到本仓库的 Skill 列表，concept-explainer 的 description 匹配成功
  • 按Skill 的指导：先上网核实定义（来源进入上下文）→ 按五板块生成 learning-materials/agent.html → 自检 → 提交 git
  • 产出保持统一结构，且全过程我只需一句话——这就是三者协作的价值：Agent 负责干，上下文负责记，Skill 负责对
