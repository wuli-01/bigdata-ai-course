🧠 大模型的上下文（Context）

一页速览 + 两关闯关测试 · 生成日期 2026-09-10

💡 我的个人理解

上下文就是模型"此刻能看见的全部信息"，像一张工作台的桌面：系统提示、聊天历史、工具返回结果、检索来的资料，全都摊在这张桌上。桌面宽度有限（按 token 计量），放不下的就被清走；模型只基于"桌上有什么"来推理——桌上没有的，它就不知道。所以用好大模型，很大程度上就是"上下文管理"这门手艺。

生活例子 🍳：厨师做菜时，操作台（上下文）上摆着订单、食材和半成品。台面就那么大，放不下的东西只能收进冰箱（外部存储）——厨师看不见冰箱里有什么，除非你重新拿出来摆上台面。而且订单压在最下面时容易被忽略，放在最显眼的位置才会被第一时间看到（位置偏差）。

⚙核心机制 / 组成

系统提示+ 对话历史+ 工具调用与结果+ 检索注入的资料→ 拼成一次请求（按 token 计量）
  • Token 计量：上下文长度按 token（词元）算，一个汉字约 1~2 个 token；窗口容量从几万到上百万 token 不等，超出就截断或压缩
  • 一次性，无记忆：模型本身无状态，"记得之前说过什么"只是因为历史被重新拼进了上下文；新会话 = 新桌面
  • 位置偏差：经典研究发现"Lost in the Middle"——信息在开头或结尾时模型用得最好，塞在长上下文中间性能明显下降
  • 上下文工程（Context Engineering）：压缩摘要、截断旧历史、RAG 检索注入、Skill 按需加载——都是为了在有限窗口里放"最有用的东西"

🎯具体应用场景（我自己的经历）

帮我 push 仓库那次，AI 助手的上下文里装着系统提示（工具规则）+ 整个会话历史（装环境、建仓库的经过）+ 每条命令的输出。正因为它"看见"了 Connection was reset 这条报错出现在上下文里，才会决定下一步去扫描可用 IP。如果开新会话（上下文清空），它就完全不知道之前做过什么，我得从头交代一遍。另外 Agent Skill 的"渐进式加载"本质也是上下文管理：平时只放一行 description，命中了才把整份说明书铺上桌面。

⚠容易混淆的问题 / 使用边界

容易混淆区别
上下文 vs 记忆"记忆"是拟人说法：短期记忆＝当前上下文，长期记忆＝靠外部存储再检索进上下文；模型本身不会记住任何东西
上下文 vs 微调微调把知识"焊进"模型参数（训练阶段、成本高、难更新）；上下文是"临时摆在桌上"（推理阶段、随时可换）。查最新资料应靠上下文注入
窗口大 vs 用得好窗口百万 token ≠ 全都能用好——中间位置的信息仍易被忽略，重要内容应放开头或结尾
  • 使用边界：放进上下文的内容会随请求发送给模型服务商，密码、token、个人隐私不要进上下文；上下文越长，费用与延迟越高
